# Tsuru blog platform plan (TSR-358)

**Status:** planned architecture; immediate landing cleanup and route fix deployed on 2026-09-29 (`fe/landing` commit `6da2b01`, Pages run `36598135442`).  
**Decision:** any signed-in Tsuru user can write and submit; a platform editor approves before publication. The public blog lives at `https://blogs.tsuru.jcampos.dev` on a separate GitHub Pages site. Editing and storage stay in Tsuru. **The API is the source of truth for all public landing and blog content; neither public site reads checked-in content JSON.**

## 1. Current state and migration boundary

- `fe/landing` owns the current `/blog` list, `/blog/:slug` detail, and six bundled articles in `src/content/blog.json`. The public site has no runtime blog API.
- The landing currently has 24 content JSON files and public imports throughout pages, navbar, footer, brand/theme startup, and SEO. Its Examples page already fetches templates from the API; the rest of the public content must move to an API-backed model.
- Its `/admin/blog` is a **development-only** JSON editor. Saving writes to the local Vite plugin in development or downloads JSON elsewhere; the production GitHub Pages build removes the admin. It is not the live `admin.tsuru.jcampos.dev` console.
- The live platform console in `fe/dashboard` has no blog route. `fe/pos-system` has no writer section. `be/management-be` has no blog model or API.
- Three posts attributed to unconnected organizations (`article2`, `article4`, `article5`) have been removed from the landing site. All three `Equipo Tsuru` posts (`article1`, `article3`, `article6`) remain by owner decision, including the Manantial story. The live sitemap contains only these three article routes; a removed route returns 404.
- The previous transition held the old detail route while `BlogDetail` read the new URL, briefly rendering the not-found state. The route now passes its matched slug to the detail component; this fix is deployed. Live browser navigation from the retained article back to the blog showed the list without the false not-found view.

## 2. Product flows and authority

1. A signed-in user opens **My blog posts** from the main app. This is an account-level feature, accessible even without an organization or a storefront permission. They can create, save, preview, edit, and submit their own draft.
2. Submission locks a reviewable revision. The author sees `Draft`, `In review`, `Changes requested`, `Published`, or `Rejected`, plus the editor's reason. An edit to a published post becomes a new draft revision while the approved version stays public.
3. A platform editor works from a **Blog review** queue in `admin.tsuru.jcampos.dev`: compare revisions, preview both languages and responsive widths, request changes, approve, unpublish, or archive. Record who did each action and when. The server enforces editor-only transitions; hiding buttons is insufficient.
4. Visitors read only approved, published revisions at `blogs.tsuru.jcampos.dev`. Draft previews use an expiring authenticated preview token, never a guessable public slug.
5. An organization may be credited only when it is a real linked organization and the author is authorized to represent it. Otherwise the byline is the user or the Tsuru team. No fabricated organization stories are seeded.

## 3. Editor and content model

Use a structured, versioned document instead of a single HTML or token string. Store a post with stable `id`, immutable `author_user_id`, optional verified `organization_id`, unique slug, bilingual title/excerpt, cover media, topic/tags, status, timestamps, SEO fields, and a sequence of revisions. Each revision stores ordered blocks and a schema version; approvals point to a revision id. Keep `published_at` as an ISO timestamp and format the date per language in the UI.

The authoring canvas should support paragraphs; H2/H3 headings; bold, italic, links, and inline code; lists; quotes; dividers; callouts; embeds on an allowlist; and image blocks. An image block stores a media id, meaningful alt text, optional bilingual caption and credit, focal/crop settings, and layout `full`, `wide`, `left`, or `right`. Left/right images share a two-column figure/text block on desktop and stack naturally on mobile; captions stay attached to the image. The editor exposes alignment, width, and caption as visible controls with a live preview rather than raw markup. Cover image and in-article images are separate roles.

Use the existing authenticated upload pattern as a starting point: a server-issued presigned upload, server validation of MIME/size/dimensions, durable object storage, and CDN URLs. Persist a media record before a post references it; generate responsive sizes and require alt text before submission. Keep media ownership and reuse explicit. Render blocks from a validated schema with safe links and an embed allowlist; do not render arbitrary author HTML.

Editing behavior: autosave with visible saved/error state, undo/redo, drag/reorder blocks, keyboard shortcuts, paste cleanup, local image progress, unsaved-change protection, language completeness indicators, desktop/mobile preview, and a clear submit-for-review action. Autosave failures must not silently discard work.

## 4. Public page design: one visual family

Reuse the Tsuru light/dark semantic colors, logo pair, serif display treatment, button shapes, and spacing rhythm from the landing. Create shared design tokens for the blog site instead of copying one page's incidental CSS. Keep body text left aligned with a readable measure of roughly 65–75 characters; remove the current justified text. Use consistent grid edges: a wide 12-column page frame, a narrower reading column, and optional media that can break into the side columns without shifting the article title or metadata. At narrow widths, all blocks become one column.

| Surface | Proposed composition |
|---|---|
| Blog home | Calm brand header and short intro; one featured story with cover image; recent cards aligned to the same grid; topic filters and search once enough posts exist; a clear sign-in/write CTA. |
| Article | Back to blog, topic/byline/date/reading time, large title and deck, cover figure, structured story blocks, author context, share/copy link, and related approved posts. |
| Empty/error | Intentional empty, loading, and retry states. Show “not found” only after a completed lookup returns no published post; never during route animation or a pending request. |

Images use `figure`/`figcaption`, maintain aspect ratio, avoid text wrapped around a narrow image on phones, and have visible captions and credits. Check contrast, keyboard navigation, focus order, reduced motion, and long ES/EN titles. The public page must work with images disabled and with no JavaScript for indexed article metadata/content.

## 5. Architecture: follow the Sóköl content/public-API pattern

The reference is the local `../Sokol-CR` workspace, particularly `be/public-be/src/api/{models,services,controllers}`, `be/public-be/scripts/gen_api_template.py`, `be/public-be/cloudformation/{identity-pool,media}.yml`, `fe/admin/src/lib/admin-store.ts`, `fe/admin/src/components/admin/OnlineContentGate.tsx`, and `fe/landing/src/repositories/content.repository.ts`. Port the contract and separation into Tsuru; do not depend on a Sóköl runtime service or copy its brand.

| Sóköl pattern | Tsuru implementation |
|---|---|
| `site_content` + `site_content_revisions`, one ordered JSON document per site/key, optimistic `base_version` with 409, revision restore | New Tsuru `be/public-be` owns versioned landing and blog-chrome documents. One-time import of the current landing entities, then the database is authoritative. Keep field order for the admin editor, validate document size/schema, and preserve audit fields. |
| `/api/public/content/{site}` through an AWS_IAM public gateway; short-lived identity-pool guest credentials sign GETs | Extend the existing `Infrastructure/public-api` allowlist to route published content and blog reads to the content Lambda. Reuse or complete Tsuru's public identity pool and scope its guest role to read-only public routes. Landing and blog bundles contain only the public gateway URL and identity-pool id, never admin/user-pool credentials. |
| `/api/admin/content/**` through a separate admin gateway; handler checks admin-pool issuer and platform-admin group | Route Tsuru CMS edits, revision restores, blog review and media creation through `admin-api.tsuru.jcampos.dev` only. Keep `/api/admin/**` out of the public and normal user gateways; test that separation and enforce admin claims again inside the handler. |
| Admin loads online documents before editors mount; save uses version match; failure shows retry | `fe/dashboard` gets landing-content editors and blog moderation. Load the server documents and versions before mounting forms. Show a shaped skeleton or retry state on failure; 409 offers reload/compare instead of overwriting another editor. |
| Presigned PUT to S3, immutable object keys, CDN media URL | Add a Tsuru blog/site media bucket or a scoped prefix in the existing upload system. Validate type, size and ownership, then issue presigned PUTs and serve immutable CDN URLs. Blog image records add alt/caption/credit/crop metadata. |

**Intentional differences:** Sóköl bundles `src/content/*.json` as an offline fallback and its CI prerender reads those files. Tsuru's requested contract forbids that fallback: public landing/blog render from API responses only, and both Pages prerenders fetch the published API. If the API is unavailable on first load, show a useful retry state; if it is unavailable during a build, fail the deploy. Sóköl does not have community authoring, so Tsuru adds an author route family on the **normal user gateway** with user-pool authentication and server-side ownership checks. It cannot be exposed through the guest role or admin gateway.

### Repository responsibilities

- **`be/public-be` (new Tsuru content/CMS service):** own `site_content`, `site_content_revisions`, blog posts and post revisions, moderation state, image registration, author ownership, and public projections. Add indexes for slug, status/date, author, and review queue; use transactions for approval and slug reservation. Its public GETs return only published revisions. The existing management API remains the identity/organization authority; the content service verifies the caller from the user-pool claims and reads linked organizations only when attribution is requested.
- **Public site-content contract:** expose a versioned `landing` document set for page copy, shared navigation/footer, brand/theme configuration, media references, and SEO metadata. Migrate every **public content** entity from the current 24 JSON files as an initial import, preserving ES/EN and page/entity structure; development inventory data does not become public CMS content. Provide a small public bootstrap response for shared chrome plus per-page reads, and a separate authenticated preview endpoint. API responses are JSON over HTTP; the prohibition is on checked-in JSON files acting as the public content source. Every publish has a content version/ETag for cache invalidation and a rebuild event. The API must serve a consistent published revision across related page entities.
- **`fe/pos-system`:** account-level writer list and full editor in the main app, using its existing Cognito session. Add a global navigation entry and route that do not depend on organization RBAC.
- **`fe/dashboard`:** review queue, moderation detail, audit trail, and editor preview using admin Cognito. Add production landing-content editing and publishing here too, replacing the landing's dev-only content CMS. Regenerate and deploy its gateway template when adding `/api/admin/**` routes, as Sóköl does for its online CMS.
- **New public blog repo/site:** a static GitHub Pages app that fetches the published API at runtime and at build time for HTML/SEO generation. Share a small typed post schema/renderer or package between writer preview and public site so layout does not drift. Never bundle admin code, a content JSON seed, or write credentials in Pages.
- **`fe/landing`:** replace public `@/content/*.json` imports and the static blog repository with typed public API queries. Load shared chrome/theme before showing page content; show a branded loading/retry state while a request is pending or fails. The not-found state appears only after an API 404. Change navbar/footer/blog CTAs to the new host. Preserve old slugs with generated redirect pages at `/blog` and `/blog/:slug`, plus canonical tags pointing to the new URLs, after the new site is live. Retire the dev-only JSON admin and remove checked-in public content JSON after migration is verified. Static image binaries and technical source code remain build assets; editorial data and copy do not.

Both GitHub Pages builds should fetch **published API data**, with no content-file fallback, to produce route HTML, canonical/OG metadata, and sitemaps. The blog build produces one readable HTML article per approved post. At runtime both sites fetch the API and honor its content version; they never hydrate from a bundled content JSON module. A failed API fetch during build fails the deploy and leaves the previous Pages release intact. Runtime errors show retry rather than stale bundled copy. Publishing landing content or approving a blog post triggers its respective Pages rebuild. If a rebuild fails, keep the last successfully built release and surface the failure to the editor. An unpublish is complete only after the Pages rebuild removes the old static HTML and sitemap entry; the API returns 404 immediately, but raw old HTML can remain reachable until that deploy completes. If instant emergency takedown is required, GitHub Pages alone cannot provide it and the hosting design needs an edge control layer.

GitHub Pages setup for the new repository: configure `blogs.tsuru.jcampos.dev` in Pages settings, add a DNS `CNAME` for that exact subdomain to `chepelcr.github.io`, enable HTTPS, set Vite base to `/`, and generate sitemap/canonical URLs for the blog host. A GitHub Actions Pages workflow deploys only the public build. Keep `tsuru.jcampos.dev` bound to the landing repository.

## 6. Delivery order and acceptance

1. **Immediate source cleanup and transition fix — deployed** — retained only the three team-authored posts in the current landing source and passed matched route params to detail. Type-check, build, prerender, Pages deploy, live sitemap, a removed-URL 404, and article-to-list browser navigation were verified.
2. **Design contract** — low and high fidelity layouts for home, article, editor, and moderation states at desktop/mobile widths; ES/EN sample copy and real team images; token, spacing, typography, and image alignment specification. Review with the owner before building the new public UI.
3. **Sóköl-style content plane and landing migration** — create the dedicated content service with document/revision tables and media, expose its public reads via the existing SigV4 guest gateway and edits via the isolated admin gateway, import public landing entities, implement typed runtime queries and API-fed SEO prerender, build the production landing-content editor in the admin dashboard, and remove public JSON imports. Compare every route in ES/EN before cutting over. Existing API-fed template examples stay API-fed.
4. **Blog backend vertical slice in the same content plane** — post/revision migration, typed block schema, draft/revision/status APIs on the authenticated user gateway, isolated admin moderation endpoints, public published projection, media upload, and contract tests for the state machine and gateway/auth boundaries.
5. **Main app editor + admin review** — complete draft-to-approval flow, including bilingual preview, caption/alignment, autosave recovery, moderation reason, and published-edit re-review. Verify with at least two user accounts plus a platform editor.
6. **Separate Pages blog** — implement the approved layouts, API-fed static article generation and runtime queries, deep links, metadata/sitemap, publish/unpublish rebuilds, DNS/HTTPS, and responsive/accessibility review.
7. **Migration and cutover** — import the three team posts with original slugs and author attribution; compare old/new content, update all landing links, add old-route redirects, verify direct navigation and search-engine metadata, then retire the dev-only JSON editors and static content files.

Release acceptance: a normal user can write with images and captions, align figures beside text, save and recover a draft, and submit it; a platform editor can request changes or approve; no pending/rejected content appears publicly; the approved ES/EN article opens directly on the new host with correct images, SEO, and mobile layout; changing or unpublishing it updates the public output; old links resolve to the matching new article; all three retained Tsuru posts remain available; navigation never flashes “Article not found.” Every public landing and blog content request, including chrome/theme/SEO, has an API source; a build check fails if public code imports `src/content/*.json` or embeds content seeds, and both API-failure and slow-loading paths show correct states. Gateway tests prove guest reads cannot write, normal users cannot moderate, and the public gateway cannot reach `/api/admin/**`.

## 7. Open implementation choices

- Select and spike an editor library against the required block schema, bilingual content, paste behavior, and keyboard accessibility before committing to it. The stored document format must remain independent of the editor package.
- Decide whether moderation notifications use the existing in-app notification channel or email as well. The review queue itself is required regardless.
- Confirm the blog repository name and who owns the DNS/Pages settings at cutover. The target domain and separate-site architecture are already decided.
